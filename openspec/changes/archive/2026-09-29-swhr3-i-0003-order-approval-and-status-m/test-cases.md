### SWHR3-R-0005 · Server-side order update processing

### SWHR3-R-0008 · Transaction atomicity for order updates

#### SWHR3-R-0008.01 · Multiple orders are updated in single transaction
- **SWHR3-C-0021** (integration, approved, v1) Three-order batch commits together in one transaction
  - Preconditions: In-memory db with PENDING orders A, B and C.
  - Step 1: Call updateOrders with A→APPROVED, B→DENIED, C→APPROVED.
  - Step 2: Read all three back.
  - Expected: Returns { updated: 3 }; A is APPROVED, B DENIED and C APPROVED, and the three rows share the same updatedAt write (a single immediate-mode transaction, SD6).

#### SWHR3-R-0008.02 · Partial batch failure triggers rollback
- **SWHR3-C-0022** (integration, approved, v1) Second update failing leaves none of the three persisted
  - Preconditions: In-memory db with PENDING orders A and C, and order B already COMPLETED.
  - Step 1: Call updateOrders with A→APPROVED, B→DENIED, C→APPROVED.
  - Step 2: Read A, B and C back.
  - Expected: Throws InvalidTransitionError naming B; A and C remain PENDING and B remains COMPLETED.
- **SWHR3-C-0023** (integration, approved, v1) Overlapping batches on the same order cannot both succeed
  - Preconditions: In-memory db with PENDING orders A and D.
  - Step 1: Commit batch 1: A→APPROVED.
  - Step 2: Commit batch 2: D→APPROVED, A→DENIED.
  - Expected: Batch 1 succeeds; batch 2 fails with INVALID_TRANSITION; A stays APPROVED and D stays PENDING.
