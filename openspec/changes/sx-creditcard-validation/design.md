# Credit Card Validation Design

## User interface

No screen records were extracted for this capability; its user interface is unspecified.

## Architecture Overview

The credit card validation capability is implemented as a two-tier system:

1. **Entity Tier**: Container-Managed Persistence (CMP) EJB entity for durable storage
2. **Value Object Tier**: Serializable data transfer object for integration scenarios

### Data Model

**CreditCardEJB Entity** (CMP 2.x):

- Abstract class with container-generated persistence
- Three CMP fields: cardNumber, cardType, expiryDate
- Local interface: CreditCardLocal (home + local)
- Primary key type: Object (container-managed/synthetic)

**CreditCard Value Object**:

- Mirrors entity fields (cardNumber, cardType, expiryDate)
- Serializable for remote transfer
- XML serialization support via DOM with DTD reference
- Used for data marshalling across component boundaries

### Card Type Enumeration

Valid card types:

1. "Java(TM) Card"
2. "Duke Express"
3. "Meow Card"

**Note**: JSP form shows display label "Meow Club" but stores value "Meow Card" — exact label-value mapping should be verified.

### Expiry Date Format

- **Storage Format**: MM/YYYY (e.g., "03/2025")
- **Component Extraction**:
  - `getExpiryMonth()` returns text before "/" (e.g., "03")
  - `getExpiryYear()` returns text after "/" (e.g., "2025")
  - Fallback defaults: "01" for month, "2010" for year when parsing fails

### Creation Methods

**CreditCardLocalHome interface** provides three overloaded `create()` methods:

1. `create(String cardNumber, String cardType, String expiryDate)` — direct parameter initialization
2. `create(CreditCard creditCard)` — value object-based initialization
3. `create()` — empty entity creation

All invoke corresponding `ejbCreate()` and `ejbPostCreate()` lifecycle methods.

### Transaction Semantics

**Container-Managed Transactions** with `trans-attribute=Required`:

- All 11 business methods and lifecycle methods (create, findByPrimaryKey, remove, getters, setters) participate
- Each method either joins existing transaction or starts new one
- ACID boundaries guaranteed by container

### Security Model

**Caller-Identity Security**:

- `use-caller-identity` declared in security-identity section
- All methods (`*`) have unchecked permission
- No role-based authorization checks
- Any caller can invoke any method

### XML Serialization

**CreditCard Value Object**:

- DTD Declaration:
  - PUBLIC: "-//Sun Microsystems, Inc. - J2EE Blueprints Group//DTD CreditCard 1.1//EN"
  - SYSTEM: "/com/sun/j2ee/blueprints/creditcard/rsrc/schemas/CreditCard.dtd"

- **toDOM(Document)**: Serializes value object to DOM node
- **fromDOM(Node)**: Deserializes DOM node to value object

XML element mapping:

- XML_CREDITCARD = "CreditCard"
- XML_CARD_NUMBER = "CardNumber"
- XML_CARD_TYPE = "CardType"
- XML_EXPIRYDATE = "ExpiryDate"

## Legacy Implementation Notes

### JSP Form Integration

**create_customer.jsp** collects card data via:

- Text input: `credit_card_number` (maxlength=30, default="0100-001-0001")
- Select dropdown: `credit_card_type` (options: Java Card, Duke Express, Meow Card)
- Separate dropdowns: `credit_card_expiry_month` (01-12) and `credit_card_expiry_year` (year values)

Form combines month + year with "/" separator before passing to create() method.

### Database Mapping

- CMP entity mapped to relational table (app-server specific)
- No schema validation enforced (e.g., no CHECK constraints on card type)
- Card type validation is application-level only
- Primary key generated by container (ORM-specific strategy)

### Key Files

- **ejb-jar.xml**: Entity declaration, lifecycle methods, transaction/security configuration
- **CreditCardEJB.java**: Abstract CMP entity class with lifecycle and accessor methods
- **CreditCard.java**: Value object with serialization support
- **create_customer.jsp**: Form UI for card data collection

## Constraints and Assumptions

1. **Card Number Length**: Assumes maxlength=30 from JSP; no database constraint enforced
2. **Expiry Parsing**: Silent defaults to 01/2010 on parse failures; may mask invalid input
3. **Card Type Validation**: Enumeration at UI level only; no database constraint
4. **Primary Key Generation**: Relies on app-server-specific CMP implementation
5. **Transaction Behavior**: Container enforces Required semantics; all methods participate
6. **XML DTD**: References external DTD file; resolution behavior depends on deployment environment
7. **Caller Identity**: All methods callable by any authenticated user; no role restrictions

## Performance Considerations

- CMP entity provides automatic persistence without explicit SQL
- Value object enables efficient data transfer without serializing entity beans
- XML serialization adds overhead; suitable for batch/integration scenarios, not high-frequency calls
- Transaction overhead applies to all operations (even read-only getters)
